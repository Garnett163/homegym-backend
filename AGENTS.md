# Правила работы над HomeGym

Эти правила действуют для всего репозитория. Проект — приложение для персональных
тренировок на Go. Явные указания пользователя имеют приоритет над этим файлом.

## Учебный формат

- Общайся на русском языке. Пользователь изучает Go: объясняй новые понятия
  простыми словами, а при первом упоминании термина кратко раскрывай его смысл.
- По умолчанию помогай пользователю писать приложение самостоятельно:
  описывай, что ему нужно сделать, и двигайся небольшими законченными шагами.
  Не реализуй следующие этапы заранее.
- Для каждого шага объясняй цель, указывай точный путь к файлу, необходимые
  изменения и команду проверки с ожидаемым результатом.
- Примеры кода должны быть понятными и достаточными для текущего шага.
  Объясняй важные решения и незнакомые конструкции Go.
- Когда пользователь просит написать или исправить код, вноси изменения сам
  в пределах запроса и затем объясняй их. Если он просит только объяснение,
  не меняй код.
- При ошибке сначала разбирай её причину, затем предлагай исправление.
- Не выбирай фреймворки, библиотеки и инфраструктуру за пользователя заранее.
  Сначала учитывай уже принятые решения и реальные требования текущего шага.

## Архитектура

Соблюдай разделение слоёв по согласованному образцу:

```text
cmd/
  api/
    main.go                  # Точка входа HTTP API
    init.go                  # Явная сборка зависимостей при необходимости
config/
  local.yml                  # Локальная конфигурация без секретов
internal/
  adapters/
    <integration>/           # Клиент конкретного внешнего сервиса
      adapter.go
      <operation>.go
  domain/
    <entity>.go               # Сущности и общие бизнес-правила
  http_handler/
    handler.go               # Зависимости HTTP-обработчиков
    <operation>.go           # Разбор запроса и формирование ответа
  repository/
    repo.go                  # Зависимости доступа к хранилищу
    <operation>.go           # Реализация операций с данными
  use_case/
    <scenario>/
      use_case.go            # Тип сценария, интерфейсы и конструктор
      handle.go              # Выполнение сценария
migrations/                  # Версионируемые изменения схемы БД
docker-compose.yml           # Окружение разработки, когда понадобится
Dockerfile                   # Сборка образа, когда понадобится
go.mod
Taskfile.yaml                # Команды разработки; имя уже принято в проекте
```

- Создавай файлы и каталоги по мере необходимости. Дерево описывает их
  назначение, а не требование сразу заполнить проект заготовками.
- Используй предметные имена приложения: например, `workout.go` и
  `create_workout`. Не копируй посторонние примеры и опечатки со схемы.
- Основная точка входа — `cmd/api/main.go`; не дублируй её корневым `main.go`.
- В `cmd/api` загружай конфигурацию, создавай зависимости, настраивай сервер
  и его завершение. Бизнес-логику сюда не помещай.
- `init.go` — имя файла для явных функций сборки. Не используй функцию Go
  `init()` для скрытого создания подключений и других зависимостей.

## Границы слоёв и зависимости

- `domain` содержит бизнес-сущности, их инварианты и предметные ошибки.
  Он не зависит от остальных слоёв, HTTP, SQL и внешних сервисов.
- `use_case` выполняет отдельный пользовательский сценарий и координирует
  работу с данными и внешними сервисами. Он может зависеть от `domain`,
  но не импортирует `http_handler`, `repository` или `adapters`.
- Интерфейсы для хранилища и внешних сервисов определяй рядом с потребителем,
  обычно в соответствующем `use_case`. Оставляй только необходимые методы.
- `repository` реализует доступ к БД; `adapters` — к внешним сервисам.
  Они удовлетворяют интерфейсам сценариев через обычную реализацию методов Go.
  Не заставляй сценарии зависеть от конкретных реализаций.
- `http_handler` разбирает HTTP-запросы, проверяет формат входных данных,
  вызывает сценарий и переводит результат или ошибку в HTTP-ответ.
  Он не выполняет SQL и не обращается напрямую к внешним сервисам.
- Бизнес-проверки выполняй в `domain` или `use_case`, чтобы они работали
  независимо от HTTP. Структуры запросов и ответов держи в транспортном слое.
- Связывай конкретные реализации в `cmd/api` и передавай зависимости через
  конструкторы. Не используй глобальные подключения к БД и клиентам.
- Поток вызовов: HTTP → обработчик → сценарий → интерфейс хранилища или
  внешнего сервиса. Конкретная реализация передаётся при запуске приложения.

## Правила Go и проверки

- Выбирай простое решение для текущей задачи. Не вводи дополнительные слои,
  универсальные репозитории и абстракции без практической необходимости.
- Сохраняй согласованные имена каталогов `http_handler` и `use_case`.
  Имена Go-пакетов делай корректными и последовательными, без дефисов.
- Передавай `context.Context` из запроса в сценарий и далее в операции
  ввода-вывода, чтобы сохранять отмену и сроки выполнения запроса.
- Обрабатывай ошибки явно; добавляй полезный контекст и сохраняй исходную
  ошибку через `%w`, когда её нужно обернуть. Не используй `panic` для
  ожидаемых ошибок и не возвращай внутренние ошибки БД в HTTP-ответах.
- Не добавляй пароли, токены и другие секреты в исходники и примеры
  конфигурации. Используй переменные окружения или локальные файлы вне Git.
- Не переписывай существующие миграции, которые могли быть применены:
  для изменений схемы добавляй новую миграцию.
- После изменения Go-кода форматируй затронутые файлы командой `gofmt`.
  Запускай подходящие проверки: `go test ./...` и `go vet ./...`.
- Добавляй содержательные тесты бизнес-правил, сценариев и исправлений ошибок.
  Для тестов сценариев используй простые подстановки зависимостей, если
  реальные БД и внешние сервисы не нужны для цели проверки.
- Сообщай, что изменено и что проверено. Если проверка не запускалась или
  завершилась ошибкой, указывай это прямо. Не выдавай ожидаемый результат
  за фактически полученный.
- Сохраняй существующие изменения пользователя. Не делай попутные
  рефакторинги и не добавляй зависимости без связи с текущей задачей.
